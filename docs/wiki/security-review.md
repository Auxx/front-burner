# Security review

> Status: **Done** for the MVP. Authentication (plan 145), git and files (plan
> 146) and the browser and secrets (plan 147) are reviewed; the
> [summary](#summary) closes the page.

The MVP's security review (`docs/product/mvp.md`, "Order of work", step 6). It
records a check of the code at one commit, not a rule: the rules are in
[security.md](../architecture/security.md), the requirements and NF-11, and this
page says whether the code keeps them.

Each section reads the code, not only the tests: a rule that has a test but can
be got around another way is a finding. Each row of a section's table names the
rule, where the code enforces it, the test that proves it, and the outcome:

- **Holds**: the code keeps the rule and a test proves it;
- **Fixed in this branch**: a finding, fixed with a test that failed before the
  fix;
- **Plan &lt;number&gt;**: a finding too large for the review's branch, with its
  own plan in Part F of the
  [step 6 index](../superpowers/plans/2026-11-16-00-roadmap-step-6.md);
- **Accepted**: a limit that the review records and the product accepts for the
  MVP, with the reason.

Paths are relative to `libs/server/`, except where they start with `apps/`.

## Authentication

Reviewed on 2026-11-20 at commit `dc256ab0`, in branch `review-auth` (plan 145):
everything that decides who a request comes from and what it may touch (A-7.2 to
A-7.5, NF-11.4, NF-11.5, REQ-AUTH-001, REQ-AUTH-003).

### Findings

Two findings, both fixed in this branch. Nothing needed a plan of Part F.

1. **A-7.5's test listed its routes.** The test that A-7.5 asks for did not
   exist as one test. Ownership was proven route by route, in each feature's
   end-to-end tests (`repositories`, `files`, `git`, `credentials`), each with
   its own hand-made list. A route added later without its own check would not
   have been noticed, and nothing checked that only the intended routes were
   public. **Fixed:** `@Public()` and `@AdminOnly()` now also mark their routes
   in the OpenAPI document (`x-front-burner-access`), which CI keeps equal to
   the code. `apps/server-e2e/src/access.e2e.spec.ts` reads every route from the
   document and checks that:
   - the public routes are exactly A-7.2's list;
   - every administrator route answers `403 forbidden` to a user who is not one,
     and every route under `/api/v1/admin/` is one;
   - every route with an ID answers another user's repository or saved
     credential exactly like a missing one (`404 not-found`). A route that needs
     a query or a body to pass validation must be given one in the test, or the
     test fails and names it.
2. **The refresh endpoint was limited per user, not per address.** LG-65 limits
   refresh by client IP. The endpoint had no rate limit group, so it fell under
   NF-11.4's general limits: 60 per address without an auth token, but 600 **per
   user** when the request carried a valid one. **Fixed:** a `refresh` group of
   60 per address per minute, NF-11.4's limit for unauthenticated requests
   _(plan's call)_. The risk was small, as a refresh token cannot be guessed
   (256 random bits), but the rule was not kept. Test: `login.e2e.spec.ts`,
   "LG-65: refreshes are limited per address, even with a valid auth token".

Accepted limits:

- **A refresh token with a known session ID and a wrong secret revokes the
  session.** The backend cannot tell such a token from a rotated one, so LG-36
  applies. The session ID is in the refresh token and in the auth token's `sid`,
  so only someone who already holds one of the session's tokens can do this, and
  all it does is log that session out.
- **The session cache keeps an entry for every session it has seen** until the
  process restarts, revoked ones excepted. Each entry is a few numbers, logins
  are rate-limited, and housekeeping deletes old sessions from the database,
  from which a missing entry is read again.

## Git and files

Reviewed on 2026-11-20 at commit `1fd6e6c0`, in branch `review-git-files` (plan
146): everything where a user's input or a remote's content becomes a path, a
git command or an outbound connection (A-7.6 to A-7.8, A-7.12, A-5.1 to A-5.10,
NF-11.6 to NF-11.8, AR-32, AR-57).

### Findings

Two findings, both fixed in this branch. Nothing needed a plan of Part F.

1. **git did not turn off `core.fsmonitor`.** The runner turns hooks off with
   `-c core.hooksPath=/dev/null`, but `core.fsmonitor` in a working copy's own
   config names a program that git runs on every `status`, just like a hook.
   Nothing writes one today: users cannot write in `.git` (A-7.6), a clone
   writes `.git/config` itself, and the engine writes only known keys. The rule
   is that git cannot run a program the repository chose, so it should not
   depend on that. **Fixed:** `-c core.fsmonitor=false` on every run, recorded
   in A-5.1. Test: `git-runner.spec.ts`, "never runs a program that the
   repository's own config names as its fsmonitor".
2. **Three IPv6 forms that embed an IPv4 address were checked as IPv6 only.**
   A-5.8 unwraps IPv4-mapped, NAT64 and 6to4 addresses, but not IPv4-compatible
   (`::169.254.169.254`), IPv4-translated (`::ffff:0:a.b.c.d`) or RFC 8215's
   local-use NAT64 prefix (`64:ff9b:1::/48`). The first two do not reach IPv4 on
   Linux without a translator, but the third does, on a network whose DNS64 uses
   it. **Fixed:** `checkAddress` unwraps all three, for the egress proxy, the
   host key probe and `EgressHttpClient` alike; A-5.8 lists them. Test:
   `address-policy.spec.ts`, "refuses the IPv4-compatible, IPv4-translated and
   local-use NAT64 forms too". A-5.8 also said that the proxy used Happy
   Eyeballs; it tries the checked addresses one after the other, and the text
   now says so.

### Findings

One finding, fixed in this branch. Nothing needed a plan of Part F.

1. **A file system error put its file's path in the log above `debug`.** Node
   writes the path of a failed file system call into the error's message, its
   stack and its `path` (for example `EACCES: permission denied, open
   '/data/repos/1/2/docs/plan.md'`). The unhandled-exception log at `error`
   printed the whole error, and the `warn` and `error` entries of the sync and
   repository features printed `String(error)`. NF-10.5 allows file paths only
   at `debug`. Nothing in normal use reaches these entries: they log failures
   that the code does not expect, such as a permission problem on the volume.
   **Fixed:** `withoutPaths` and `errorForLog` (`core/observability`) replace
   the paths of such an error with `<path>` and keep its code and system call.
   The exception filter logs unhandled errors through `withoutPaths`, and every
   `warn` or `error` entry that printed `String(error)` uses `errorForLog`.
   Tests: `api-exception.filter.spec.ts`, "NF-10.5: logs an unhandled file
   system error without the file's path"; `error-for-log.spec.ts`. Paths that
   the backend builds from IDs, such as a working copy's folder, are not file
   paths in NF-10.5's sense and stay (NF-10.4).

The MVP's security review read authentication, git and files, and the browser
and secrets against their rules. It found five problems, all fixed with a test
that failed before the fix; none needed a plan of Part F.

| Finding                                                                                | Section                                     | Outcome           |
| -------------------------------------------------------------------------------------- | ------------------------------------------- | ----------------- |
| A-7.5's test listed its routes; nothing checked that only the intended ones are public | [Authentication](#authentication)           | Fixed in plan 145 |
| The refresh endpoint was limited per user, not per address (LG-65)                     | [Authentication](#authentication)           | Fixed in plan 145 |
| git did not turn off `core.fsmonitor`                                                  | [Git and files](#git-and-files)             | Fixed in plan 146 |
| Three IPv6 forms that embed an IPv4 address were checked as IPv6 only (A-5.8)          | [Git and files](#git-and-files)             | Fixed in plan 146 |
| A file system error put its file's path in the log above `debug` (NF-10.5)             | [Browser and secrets](#browser-and-secrets) | Fixed in plan 147 |

The limits the review accepts are in each section. Two of them are the product's
own, from security.md, and an operator should know them:

- **git runs as the backend's user (A-7.12).** A rootless container cannot
  switch users, so nothing but NF-11.6 to NF-11.8 and A-5.1 stands between git
  and the backend's files. A repository cannot make git run a program of its
  choosing (see [Git and files](#git-and-files)), but a flaw in git itself would
  reach everything the backend can reach. Keep the image up to date: each
  release is scanned (NF-11.10).
- **The preview may load images from any `https:` host (A-7.13),** so that
  remote images can be shown when the user asks. If both sanitising steps were
  ever bypassed, a file could make the browser load an image from a host it
  chose, for example to learn that the file was opened. It still could not run
  script. Remote images load only after **Show remote images**, without a
  referrer.

The rest are smaller and listed where they apply: the private networks trusted
by default ([NF-11.4](#nf-114-nf-115-and-trust-proxy)), names that reach `.git`
on file systems other than Linux's ([A-7.6](#a-76-paths-from-a-client)), a
network's own DNS64 prefix, the auth token in `localStorage` and the names left
there after logout ([NF-3.5](#nf-35-and-lg-40-what-the-browser-keeps)).
