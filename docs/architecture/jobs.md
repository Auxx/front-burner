# Front Burner — Job runner

> Status: **Draft**

How background work is stored, scheduled and run. Lives in `server/jobs` (A-2).
See [overview.md](overview.md) for the numbering conventions.

## A-6: Design

- **A-6.1** We write our own runner. Ready-made queues assume Redis or Postgres,
  and our needs are small (NF-4.3).
- **A-6.2** Jobs are rows in a `jobs` table: type, owner (user and repository,
  when there is one), JSON payload, status (`queued`, `running`, `done`,
  `failed`, `cancelled`), time to run, attempts, progress, result or error code,
  and an optional **dedupe key** that is unique among unfinished jobs.
- **A-6.3** Payloads never contain secrets. A clone, fetch, pull or push that
  uses an unlocked key (AR-49, RC-19) keeps its copy of the key in an in-memory
  map keyed by job ID (`JobKeys`), removed whenever the job ends. It is lost on
  restart, which is fine: an interrupted clone or push fails (AR-54). Other
  credentials are read when the job runs, so credentials replaced meanwhile are
  used.
- **A-6.4** A loop in the backend process claims due jobs atomically (`UPDATE …
  RETURNING`). Enqueuing wakes the loop at once; otherwise it checks for
  scheduled jobs every second.
- **A-6.5** Each job type belongs to a **concurrency pool**: clones
  (`FRONT_BURNER_CLONE_CONCURRENCY`, default 2, AR-52), fetches and sync cycles
  (4), email (1), housekeeping (1). The git engine's per-repository queue
  (A-5.3) still serialises work on each working copy. _(My call: the sizes of
  the last three pools.)_
- **A-6.6** Progress and results are published on the push channel (A-3.11).
  Metrics cover queue depth, durations and failures per type (NF-10.11).

- **A-6.7** _(My call.)_ The 2-minute background fetch interval is a constant,
  not an operator setting, until a reason to change it appears.
- The **database snapshot** (`database.snapshot`, NF-6.2, A-4.12) runs every
  hour; its first run, and an overdue run after a start, run at once rather than
  spread (A-6.8). It writes a snapshot only when the newest daily one is
  `FRONT_BURNER_DB_SNAPSHOT_INTERVAL` old or there is none. The age of the
  newest file decides, not the job's schedule, so that a fresh instance has a
  snapshot a moment after it starts, a crash loop writes at most one and a
  restart never restarts the interval. Every run prunes, so that a lowered
  `FRONT_BURNER_DB_SNAPSHOT_KEEP` and a crash's partial files take effect within
  the hour. A failed snapshot or prune is logged at `error`, each with its own
  message, and the next run tries again; only a failed snapshot fails the run.
  _(Plan 129's call.)_
- The **disk space check** (`storage.disk-check`, NF-9.7) runs every minute, its
  first run at once. It calls `DiskMonitor.check()` in `server/core/storage`,
  which also checks once on start, before the instance listens. The monitor
  reads `statfs` of the data directory and of the repositories root, once when
  both are one file system (reported as `data`), and is **low** while either has
  less free space than `FRONT_BURNER_LOW_DISK_THRESHOLD` (`0` turns it off). It
  logs a `warn` on becoming low and an `info` on leaving it, with the free bytes
  per volume and no paths. A volume that cannot be read counts as not low,
  logged once until it can be read again, so that a broken check never blocks
  clones. It publishes no event: the storage library knows neither users nor
  sessions. While low, readiness is `degraded` (still `200`) and new clones are
  refused (A-3.2g). _(Plan 131's call.)_

## A-6: Restart

- **A-6.8** On startup, jobs left `running` are resolved by type as in NF-9.5
  before the loop starts. Overdue scheduled jobs of the types that ask for it,
  such as housekeeping, are spread over the first two minutes instead of all
  running at once. _(My call: which types, and two minutes.)_
