# Pull, Fetch Notices, Branches and Conflict Resolution — Plan Index

> Status: **Accepted**

Plans 42 to 67 finished MVP step 3, except the leftovers named in
[its index](2026-11-02-00-roadmap-step-3.md). This index splits MVP step 4
(`docs/product/mvp.md`, "Order of work": pull, fetch notices, branches and
conflict resolution) into small plans, numbered on from 68. Each plan is one
branch and one pull request, leaves CI green, and can be shown to someone when
it is merged. At the end of step 4 the operator creates and switches branches,
is told when the remote changes, and pulls, resolving any conflict in the
browser or aborting it. This is exit criteria 8 and 9 of the MVP, and exit
criterion 10 for pull and fetch.

There is no separate design spec: the requirements and the architecture
documents are the spec. Each plan names the requirement IDs it implements and
records its own decisions as _(plan's call)_; a decision that changes or adds to
an architecture document updates that document in the same pull request.

## Shared constraints

The shared constraints of [the step 1 index](2026-10-26-00-roadmap.md),
[the step 2 index](2026-10-28-00-roadmap-step-2.md) and
[the step 3 index](2026-11-02-00-roadmap-step-3.md) apply to every task of every
plan here, with these additions. The git commands that the plans name were run
against git 2.56 when these plans were written, on a throwaway repository.

- **Library homes.** Git operations go into `server/core/git`: `GitEngine` keeps
  network operations and status, `GitMerge` (plan 76) has merges and conflicts,
  and `GitBranches` (plan 84) has branches. All three use `LocalGit` (plan 68).
  Endpoints and jobs go into `server/feature/sync`, and UI into
  `feature-repository-screen`, except the editor's conflict extension, in
  `web/code-editor`.
- **A network job** (`sync.push`, `sync.fetch`, `sync.fetch-background`,
  `sync.pull`) is in the `fetch` pool (A-6.5), takes its network step inside
  `NetworkLock.run` and nothing else there (A-5.3), holds a protected key as
  `JobKeys` does (RC-19), and reports what git refused as a `failed` outcome
  with its params (plan 57). Only `sync.fetch-background` is requeued after a
  restart (NF-9.5).
- **A refusal first, at the request, and again where it counts.** A request
  refuses what it can see, but a save can arrive while a pull is fetching, so a
  job checks again inside the working-tree lock (A-5.3).
- **Merges take no shortcut name.** `git merge` gets
  `refs/remotes/origin/<branch>`, never `origin/<branch>`: with a local branch
  named `origin/main`, the short name means that branch, and the pull says
  "Already up to date" without having merged anything.
- **A name from a client is never an option.** Every git command that takes a
  client's branch name puts it after `--` or checks it first: `git switch
  --orphan=x` empties the working copy.
- **A merge never overwrites an ignored file.** Git protects one only in a
  fast-forward, and aborting can't bring it back, so `GitMerge.merge` refuses
  with `merge-blocked` before it starts (plan 76).
- **A conflicting file on disk** is read and written through
  `resolveInWorkingCopy(root, path, { symlinkLeaf: true, mayBeMissing: true })`
  (A-7.6), also when git named the path: a folder on the way can be a symbolic
  link.
- **Every merge passes** `-c merge.conflictStyle=merge`, `-c
  rerere.enabled=false`, `-c commit.gpgsign=false`, `-c core.commentChar=#`,
  `--no-autostash` (nothing is stashed, D-4.3) and the commit author's
  `GIT_AUTHOR_*` and `GIT_COMMITTER_*` variables (CA-2), whatever the working
  copy's configuration says.
- **The API and code say ours and theirs,** as the glossary has it, with the
  kind `deleted-by-us`. "Mine" is the UI's word for ours, as in **Use my
  version** and "Mine (main)".
- **`git checkout -m` is never used.** It labels markers `ours` and `theirs`,
  and GC-5 wants branch names; `git merge` itself labels mine `HEAD`.
  `GitMerge.writeMarkers` (plan 76) is the one way to write the markers that a
  user sees.
- **A merge's state comes from git** (A-4.5). `git ls-files -u` lists unresolved
  files, and `git ls-files --resolve-undo` the resolved ones, with the same
  stages. Only the recorded commit and the merge commit it belongs to are in
  `sync_state` (A-4.5a).
- **Events.** A merge starting or ending, a file resolved, and a fetch that
  moved a remote branch publish `git.changed`, and `files.changed` when files
  changed. The `remote.changed` and `merge.state` events that A-3.11 sketched
  are not built: clients read `GET …/git/status`, `…/git/incoming` and
  `…/git/merge` over REST, which they must after a reconnect anyway. _(Plans 70
  and 81 update A-3.11.)_
- **New Angular artefacts come from `toolkit-nx`,** and templates follow
  `angular-templates`.
- **Verifying a plan's last task:** `npm run format`; `node
  tools/ai-tools/src/bin/doc-ids.mjs check`; `npx nx affected -t
  typecheck,lint,test,build,size-check`; and, when the API changed, `npx nx run
  web-api-client:generate`. CI runs the end-to-end suites too; a plan's steps
  name the ones that prove it.
- A test that covers only part of a criterion does not start with its ID (the
  step 3 index explains why). Each criterion is named by one plan, as its steps
  say.
