# Fetch API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Plan 70 of [the step 4 index](2026-11-08-00-roadmap-step-4.md): `POST
…/git/fetch` starts a fetch job, a client can read what is incoming, and the
status says why the last fetch failed.

**Architecture:** `FetchStep` is the one piece that fetches for a job: it takes
the network lock, runs the engine and stores the outcome in the new `sync_state`
table, so that a pull (plan 77) and a background fetch (plan 72) share it. Only
a fetch that changed something publishes `git.changed`, so that an idle tab does
not read status every 2 minutes for nothing _(plan's call)_. There is no
`remote.changed` event: the client reads `GET …/git/incoming` when `behind`
changes, which replaces the changed paths that A-3.11 sketched and works after a
reconnect too _(plan's call)_.

**Tech Stack:** as before. No new packages. `sync_state` is the first of its
columns; plan 77 adds the recorded commit and step 5 adds the rest.

**Spec:** `docs/requirements/git-advanced.md` (GA-3, GA-33's **Fetch**, GA-34's
counts); `docs/requirements/repo-credentials.md` (RC-3, RC-4, RC-19);
`docs/architecture/data.md` A-4; `docs/architecture/jobs.md` A-6.3.

## Global Constraints

- The shared constraints of [the step 4 index](2026-11-08-00-roadmap-step-4.md)
  apply.
- The job type is `sync.fetch`, dedupe key `fetch-now:<repositoryId>`,
  `onInterrupted: 'fail'`, `maxAttempts: 1`. It is allowed during a merge
  (GC-3).
- The request refuses only `key-locked` and `credentials-missing`, from
  `SavedCredentialsService.keyForJob` (a fetch the user started keeps the unlock
  alive, AR-31).
- A repository without credentials fetches anonymously; `auth-failed` is then
  `no-credentials` (RC-4).
- `key-locked` is never stored in `sync_state`: a key is locked per session
  (RC-20), and the row is per repository. `FetchStep` returns it as a failure
  and leaves the stored problem as it was.

## Review Focus

- **A public repository without credentials** fetches → Task 2 test `fetches
  without credentials`.
- **A failure, then a success,** clears the problem, and a second failure
  replaces it → Task 2 test `keeps only the last fetch's problem`.
- **A secret in `sync_state`:** the problem stores a code and params, and the
  params of a host key are public → Task 2 test `stores no secret`, with a token
  in the remote's refusal.
- **A file path that looks like a pathspec, or is inside `.git`,** on `incoming`
  is refused like any other path (A-7.6) → Task 2 test `refuses a path inside
  .git`.
- **A fetch during a merge** must run and leave the merge alone (GC-3) → Task 2
  test `fetches during a merge, which stays`.

**Interfaces:**

- Consumes: `GitEngine.fetch`, `GitEngine.incoming`, `NetworkLock`,
  `JobCredentials`, `networkFailure`, `KnownHostsService.linesFor`,
  `SyncStateStore`, `GIT_JOB_TYPES`.
- Produces:
  - `FetchStep.run(job: { id: number; userId: number; repositoryId: number }):
    Promise<{ ok: true; moved: boolean } | { ok: false; failure: GitJobFailed
    }>`, which stores the problem or clears it, and publishes `git.changed` when
    `moved`, or when the problem changed.
  - `POST /api/v1/repositories/:id/git/fetch` (`fetch`, `202`, `GitJobStarted`).
  - `GET /api/v1/repositories/:id/git/incoming?path=` (`incoming`,
    `GitIncoming`: `{ upstream: string; commits: number; touchesPath: boolean }
    | null` wrapped as `{ incoming: … }`).
  - `GIT_NETWORK_JOB_TYPES` gains `'fetch'`, and `GIT_JOB_TYPES` `'sync.fetch':
    'fetch'`. `GitJobOutcome` gains `GitFetched`: `{ kind: 'fetched'; moved:
    boolean }`.
  - `GitStatus.fetchProblem: GitProblemState | null`.
