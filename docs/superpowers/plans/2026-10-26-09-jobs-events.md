# Job Runner and Push Channel Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Plan 9 of [the index](2026-10-26-00-roadmap.md): the backend runs
background jobs from a database table in concurrency pools, survives restarts as
NF-9.5 says, cleans up expired sessions and old login audit entries, and pushes
small notifications to each logged-in tab over Server-Sent Events, which the web
client reads and reconnects to on its own.

**Architecture:** Two new core libraries. `server/core/jobs` stores jobs in a
`jobs` table and claims them with `UPDATE … RETURNING` in a loop woken by
`enqueue` or a one-second tick (A-6.1 to A-6.5, A-6.8); features register job
types with their handler, pool and restart rule. `server/core/events` keeps the
open SSE streams per user and session and publishes typed events from
`shared/contracts` (A-3.10, A-3.11). The web client's `PushChannelService` in
`web/core` reads the stream with `fetch`, so the auth token travels in the
header (A-8.5). The `repository_id` column of `jobs` comes with plan 11, which
is the first plan with repository jobs.

**Tech Stack:** as before. No new packages.

**Spec:** `docs/architecture/jobs.md` A-6.1 to A-6.6, A-6.8 and the job types
**Clone** (pool and per-user limit only) and **Housekeeping** (session cleanup,
login audit retention, old jobs); `docs/architecture/api.md` A-3.10, A-3.11;
`docs/architecture/web-client.md` A-8.5; `docs/requirements/auth-login.md`
LG-38, LG-45; `docs/architecture/non-functional.md` NF-4.3, NF-9.2, NF-9.5,
NF-11.4 (3 clones per user); `docs/architecture/overview.md` A-1.13, A-1.14,
A-1.15 (`FRONT_BURNER_CLONE_CONCURRENCY`); `docs/architecture/security.md` A-7.2
(revoking closes streams).

## Global Constraints

- The shared constraints of [the index](2026-10-26-00-roadmap.md) apply.
- Uses plan 1's `RequestAuth`, `AuthMiddleware`, `SessionService` and the
  `Config` durations, and plan 6's repository status enums.
- Job payloads and results never contain a secret (A-6.3); a test in Task 3
  checks the stored row of a job enqueued with a payload.
- Events are notifications, not state: small payloads, never replayed; after
  every (re)connect the web client fetches current state over REST (A-3.11).
- The SSE endpoint is left out of the OpenAPI document
  (`@ApiExcludeController`); the web client reads it with `fetch`, the one
  exception to the generated client (A-8.5).
- The web client's push code is not imported by `@front-burner/web-core/app`: it
  reaches the bundle only through lazy features (NF-2.9).

## Review Focus

- **Two requests enqueuing the same deduplicated job at once** must leave one
  unfinished job, and the second `enqueue` must return the first one's ID → Task
  1 test `allows one unfinished job per dedupe key` and Task 3 test `returns the
  existing job for a duplicate`.
- **A clone running when the backend stops** must be failed on the next start,
  never run again (AR-54, NF-9.5) → Task 4 test `fails an interrupted job whose
  type says so`.
- **A stream whose session is revoked or whose auth token expires** must be
  closed by the backend, not left open as an authenticated channel → Task 2
  tests `closes the streams of a revoked session` and `closes a stream when its
  auth token expires`.
- **A proxy that buffers or closes idle streams** must still deliver events at
  once and keep the stream open (A-3.10) → Task 2 tests `sets the headers that
  stop buffering` and `sends a comment every 30 seconds`.
- **The backend restarting under an open tab** must lead the web client to
  reconnect with backoff and tell services to reload their state, without a page
  reload → Task 5 tests `reconnects with backoff` and `announces every
  reconnect`.

### Task 3: `server/core/jobs`: the runner

**Files:**

- Create (generated): `libs/server/core/jobs` (`@nx/nest:library`,
  `server-core-jobs`, tags `scope:server,type:core`)
- Create: `src/runner/job-runner.ts` (+ `.spec.ts`), `src/runner/job-types.ts`,
  `src/jobs.module.ts`
- Modify: `libs/server/core/config/src/config/*` (+ spec):
  `FRONT_BURNER_CLONE_CONCURRENCY` (integer 1 to 16, default 2)
- Modify: `apps/server/src/app/app.module.ts`

**Interfaces:**

- Consumes: `jobs` (Task 1), `EventsHub` (Task 2), `Config.cloneConcurrency`.
- Produces:
  - `JOB_POOLS = { clone: config.cloneConcurrency, fetch: 4, email: 1,
    housekeeping: 1 }` (A-6.5).
  - `JobTypeDefinition<P, R> = { type: string; pool: keyof JOB_POOLS; handler:
    (job: RunningJob<P>) => Promise<R>; onInterrupted: 'fail' | 'requeue';
    maxAttempts?: number (default 1); retryDelayMs?: (attempt: number) =>
    number; perUserLimit?: number }`.
  - `RunningJob<P> = { id: number; userId: number | null; payload: P; attempt:
    number; signal: AbortSignal; reportProgress(percent: number): void }`.
  - `JobRunner` (injectable):
    - `register(definition): void` — called by features in `onModuleInit`;
    - `enqueue(request: { type: string; userId?: number; payload: object;
      runAt?: Date; dedupeKey?: string }): number` — inserts and wakes the loop;
      on a dedupe conflict returns the existing unfinished job's ID; throws
      `ApiErrorException(429, 'too-many-jobs')` when the type's `perUserLimit`
      of queued or running jobs is reached (NF-11.4: clones use 3);
    - `cancel(where: { id?: number; userId?: number; types?: string[] }): void`
      — queued ones become `cancelled`; running ones get their signal aborted;
    - the loop: for each pool with a free slot, claims the next due job of its
      types with `UPDATE jobs SET status = 'running', attempts = attempts + 1
      WHERE id = (SELECT … ORDER BY run_at, id LIMIT 1) RETURNING *` (A-6.4); a
      handler that resolves → `done` with `result`; throws → `failed` with
      `errorCode` (`error.code` when it is a string, else `'failed'`), or
      `queued` again at `now + retryDelayMs(attempt)` while attempts remain;
      publishes `job.progress` (at most once a second per job) and
      `job.finished` to the job's user (A-6.6);
    - `beforeApplicationShutdown`: stops claiming, aborts running jobs, waits up
      to 25 seconds for them (A-1.14).
  - `ERROR_CODES` gains `'too-many-jobs'`.

- [ ] **Step 1: Write the failing tests** (test database, a fake `EventsHub`,
      fake timers where noted): `runs a job and stores its result`; `runs at
      most the pool's size at once` (three clone jobs, concurrency 2: the third
      starts when one finishes); `runs a job at its time` (`runAt` in 5 s);
      `returns the existing job for a duplicate`; `refuses more than the
      per-user limit`; `records the error code of a failed job`; `retries with
      the delay while attempts remain`; `publishes progress and the outcome to
      the job's user`; `cancels a queued job and aborts a running one`;
      `shutdown aborts running jobs`; `refuses a payload with a secret-looking
      key` (`password`, `token`, `secret`, `privateKey` or `passphrase` at any
      depth throws, so a secret cannot reach the table by mistake, A-6.3).
- [ ] **Step 2: Run them and see them fail** — `npx nx test server-core-jobs`.
- [ ] **Step 3: Implement.**

### Task 4: Restart rules, repeating jobs and housekeeping

**Files:**

- Modify: `libs/server/core/jobs/src/runner/job-runner.ts` (+ `.spec.ts`)
- Create: `libs/server/feature/auth/src/housekeeping/auth-housekeeping.ts` (+
  `.spec.ts`)
- Create: `libs/server/core/jobs/src/housekeeping/finished-jobs-cleanup.ts` (+
  `.spec.ts`)
- Modify: `docs/architecture/jobs.md` A-6.8 (only types marked `spreadOnStart`
  are spread) _(plan's call)_

**Interfaces:**

- Produces:
  - `JobTypeDefinition` gains `repeatEveryMs?: number` and `spreadOnStart?:
    boolean`.
  - `JobRunner.start()` (from `onApplicationBootstrap`, after every feature
    registered its types): first resolves every `running` row by its type's
    `onInterrupted` (`'fail'` → `failed` with `errorCode: 'interrupted'`;
    `'requeue'` → `queued`), and a running row of an unknown type → `failed`;
    then moves the `runAt` of overdue jobs of `spreadOnStart` types to a random
    time within the next 2 minutes (A-6.8); then makes sure each repeating type
    has one unfinished job (dedupe key `repeat:<type>`); then starts the loop.
    After a repeating job finishes, the next one is enqueued at `now +
    repeatEveryMs`.
  - Housekeeping types (pool `housekeeping`, `onInterrupted: 'requeue'`,
    `spreadOnStart: true`):
    - `auth.session-cleanup` every hour: deletes sessions whose `expiresAt` or
      `revokedAt` is in the past (LG-38);
    - `auth.login-audit-retention` every day: deletes `login_audit` rows older
      than `loginAuditRetentionMs` (LG-45);
    - `jobs.cleanup` every day: deletes `done`, `failed` and `cancelled` jobs
      finished more than 7 days ago (A-6 job types).

- [ ] **Step 1: Write the failing tests**: `fails an interrupted job whose type
      says so`; `requeues an interrupted job whose type says so`; `fails a
      running job of an unknown type`; `spreads overdue housekeeping over two
      minutes`; `keeps one repeating job per type`; session cleanup `deletes
      expired and revoked sessions only`; retention `deletes entries older than
      the retention only` (with `FRONT_BURNER_LOGIN_AUDIT_RETENTION=1d`); jobs
      cleanup `keeps unfinished and recent jobs`.

### Task 5: The push channel client in `web/core`

**Files:**

- Create (generated service):
  `libs/web/core/src/core/services/push-channel/push-channel.service.ts` (+
  `.spec.ts`)
- Create: `libs/web/core/src/core/services/push-channel/sse-parser.ts` (+
  `.spec.ts`)
- Modify: `libs/web/core/src/index.ts` (not `app.ts`)

**Interfaces:**

- Consumes: `AuthSessionService` (plan 2), `PushEvent` (Task 2, type only).
- Produces:
  - `parseSse(chunk: string, state: SseParserState): { events: { type: string;
    data: string }[]; state: SseParserState }` — handles events split across
    chunks, comment lines and `\r\n`.
  - `PushChannelService` (`providedIn: 'root'`):
    - `events: Observable<PushEvent>` — shared; the stream opens on the first
      subscriber while logged in and closes with the last one or on logout;
    - `reconnected: Observable<void>` — emits after every successful
      (re)connect, the first included, so that services reload their state
      (A-3.11);
    - connects with `fetch('/api/v1/events', { headers: { Authorization },
      signal })`; reconnects after an error or a closed stream with backoff 1,
      2, 5, 10, 30, 30 … seconds, reset after a connection that lasted 60
      seconds; a `401 auth-token-expired` first calls
      `AuthSessionService.refresh`; a `401 unauthenticated` stops (the
      interceptor's expiry handles the rest); reconnects at once when the page
      becomes visible again and the stream is closed (A-8.5). Events that do not
      parse as `PushEvent` are dropped (checked by `type` only, no Zod in
      `web-core`).
