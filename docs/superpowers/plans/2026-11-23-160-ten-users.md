#### The cause (2026-11-24)

Measured on plan 152's droplet, image `f9c295c`, among the 2,500 working copies.
`perf-api.mjs run` gained `--measures` (one operation at a time),
`--metrics-token-file` (the load while the measures run) and `--instance-pid`
(CPU split into the instance's Node.js process, the rest of its container, and
the rest of the host); a new tool, `cpu-profile.mjs`, summarises a profile taken
with `NODE_OPTIONS=--cpu-prof` in the container.

**NF-2.1, the folder, alone** (`--measures folder`, p95 692 ms): the host used
1.52 of its 2 cores, of which the instance's Node.js process **1.04**, its git
0.38 and the tool 0.10. The main thread was the limit: busy 94% of the time, the
event loop's delay up to 181 ms (p99). Per listing it spent about 60 ms:

| Main thread, per listing of 1,000 entries           | Share | About |
| --------------------------------------------------- | ----- | ----- |
| `child_process.spawn` (4 gits: libuv forks Node.js) | 45%   | 27 ms |
| `fs.promises.lstat` of 1,000 entries                | 19%   | 11 ms |
| Express, Nest, auth, the database, JSON             | 36%   | 22 ms |

`spawn` blocks the event loop for as long as the fork takes, and a fork copies
the page tables of the whole process: 0.6 ms at 55 MB resident and 4.6 ms at 370
MB on a developer machine; the instance held 147 MB after a start and 317 MB
after a day of plan 152's runs, about 7 ms per git on the droplet.

**NF-2.6, pull and push alone** (`--measures push,pull`): the host was full
(1.97 cores; load 8.4), of which the instance's Node.js process 0.27, its git
0.69 and the tool with its git server **1.02**: the remote's side, which in use
is the git host's. The main thread spent 72% of its time blocked in `spawn`,
whose forks wait for a CPU too. Each job ran for 1.9 s (pull) and 1.1 s (push)
on average and waited as long again for one of the `fetch` pool's 4 places (at
most 6 queued). A pull ran 7 gits and a push 9 (the config was read twice, in
two gits, before each network command).

**What the tool measured.** Each of its users sends the next request the moment
the last one ends. 10 such users keep the instance at full load all the time,
where by Little's law a response takes about 10 times the cost of one request at
the bottleneck: 10 × 60 ms = 600 ms for the folder, against p50 564 ms measured.
At that load, NF-2.1 needs a listing to cost under 30 ms of the main thread;
without any git or `lstat` at all it would still cost 22 ms of framework. That
is a load test, not 10 people at work.

**A zombie per git operation.** The image ran `node main.js` as PID 1. git's
detached auto-maintenance (`git maintenance run --auto --detach`, after a fetch,
a merge or a commit) leaves its process to PID 1, and Node.js never reaps it:
after plan 152 the container held 3,344 zombies, exactly its fetches, merges and
commits, against a pids limit of 4,653. About 1,300 more and no git starts.

#### The fix _(the operator's decision of 2026-11-24, recorded at NF-1.2)_

1. **NF-1.2 is measured with think time.** `perf-api.mjs run --users` pauses
   each user 5 seconds on average (2.5 to 7.5, evenly) before each operation
   (`--think`); `--think 0` stays available as a load test. Recorded at NF-1.2
   in `non-functional.md`, and in the run sheet.
2. **Fewer gits, where it is cheap.** The config check before a network command
   reads the remote's URL from its own `git config --list` (one git, not two:
   one fewer per fetch, two per push); a folder listing asks the index for its
   gitlinks and for the submodule it lies in with one `ls-files` (three gits,
   not four).
3. **`tini` is the image's PID 1** (NF-11.11), so zombies are reaped; the
   container suite checks it.

Moving git's forks to a small helper process, or the listing off the main
thread, is left out: with think time the main thread is far from full, and both
are large changes.

#### What the first measure with think time found (2026-11-24)

With the pauses, on the old image, every row passed but the pull: p95 1,349 ms
added (the job's run time 813 ms on average, against git's 170 ms), the host at
0.65 cores and no job waiting. On the image with fixes 1 to 3 it was 1,529 ms. A
timed trace of one pull showed 21 gits, and most of the time in the fetch's
three HTTPS requests: each opened a new connection through the egress proxy, and
on each, git's curl (GnuTLS) read the 297 files of `/etc/ssl/certs` before the
TLS handshake. In the container, one `git ls-remote` took 130 ms with that
folder and 42 ms without it, with verification unchanged.

4. **git reads the certificate bundle, not the folder** (A-5.1 in
   `git-engine.md`): unless `SSL_CERT_DIR` is set, every git gets `-c
   http.sslCAPath=` and `GIT_SSL_CAINFO` names
   `/etc/ssl/certs/ca-certificates.crt`, or, when the operator set
   `GIT_SSL_CAINFO`, a file written once per process with that bundle followed
   by the operator's file, which is what the folder and the file trusted
   together (AR-43). The pull alone, 10 users with the pauses: p95 800 ms added,
   the job 508 ms on average.
5. **The backend exits 0 after a clean stop under `tini`**: Nest raised the
   signal again after its hooks, which PID 1 ignores but any other process dies
   of (exit code 143); `enableShutdownHooks` now ends with `process.exit(0)`
   (`useProcessExit`), as the container suite checks (NF-9.2).
