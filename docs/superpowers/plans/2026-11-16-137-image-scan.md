# Image Scan Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Plan 137 of [the step 6 index](2026-11-16-00-roadmap-step-6.md):
`tools/docker/Dockerfile` becomes the release image, and CI builds it and scans
it with Trivy on every push to `master` and on every pull request that changes
what goes into it, failing on a high or critical vulnerability that has a fix
(NF-11.10's second bullet, NF-11.11).

**Architecture:** The Dockerfile already builds what NF-11.11 asks for (slim
base, Node.js, git, `openssh-client`, UID 1000); its header comment says it is
"not the production image" only because nothing scanned, signed or published it.
_(Plan's call: one Dockerfile for testing and release, so that what is tested is
what ships.)_ A new CI job, `image`, builds it with Buildx and the GitHub
Actions cache, loads it locally, and runs `aquasecurity/trivy-action` with
`scan-type: image`, `severity: HIGH,CRITICAL`, `ignore-unfixed: true`,
`exit-code: 1` and the existing `.trivyignore`. Plan 138 reuses the job's image,
and its smoke test is what proves the image's user and git (NF-5.6, A-5.7).

The image is scanned in CI only. A developer's local scan stays what it is now:
Trivy on `package-lock.json`, as the `trivy` job runs it.

**Tech Stack:** `docker/setup-buildx-action`, `docker/build-push-action`,
`aquasecurity/trivy-action`, all pinned to SHAs.

**Spec:** `docs/architecture/non-functional.md` NF-11.9 to NF-11.11, NF-5.6.

## Global Constraints

- The shared constraints of [the step 6 index](2026-11-16-00-roadmap-step-6.md)
  apply.
- The job needs no secrets and pushes nothing.
- A finding that can't be fixed yet goes into `.trivyignore` with a comment
  saying why and until when; never a lower severity threshold.
- The job always runs on a push to `master`. On a pull request it is skipped
  when every changed file is one the image does not contain. A first step
  compares the pull request with its base (`git diff --name-only`) and leaves
  out:
  - `docs/**` and every `*.md`;
  - tests and stories: `**/*.spec.ts`, `**/*.stories.ts`, `**/.storybook/**`,
    `apps/web-e2e/**`;
  - `apps/server-e2e/**`, except the container suites (`container*.e2e.spec.ts`
    and `support/container*`), which plan 138 runs in this job;
  - `tools/ai-tools/**`, `tools/lint-rules/**`;
  - `.github/**`, except `ci.yml` and `.github/actions/**`.

  Everything else may change the image, so it runs. _(Plan's call: a list that
  skips, not one that runs, so that a new folder is scanned until someone says
  otherwise.)_ The OS packages change without a commit, so plan 139's release
  scan is the final word.

## Review Focus

- **A base image update** that brings a vulnerability fails the next run on
  `master`, not silently later → the job runs on every push to `master`.
- **A pull request that changes only docs or tests** does not build the image →
  the skip step, tried in step 2 against two sample lists of files.
- **A change to a library the server or web client uses** is never skipped → the
  same check.
