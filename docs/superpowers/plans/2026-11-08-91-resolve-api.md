**Goal:** Plan 91 of [the step 4 index](2026-11-08-00-roadmap-step-4.md): `POST
…/git/merge/resolve` marks a file as resolved with its saved content, or
resolves it with a whole version, or keeps or deletes a file one side deleted.

**Architecture:** One endpoint with one `resolution`, since they differ only in
what they put in the working copy before the file is added to the index.
Resolving goes through `MergeGuard`, so it waits for any save in progress. Each
is written to the working copy at once, so it survives a restart and any device
sees it (GC-4). The backend refuses leftover markers unless told to go ahead, so
that every client asks (vision goal 12).

**Tech Stack:** as before. No new packages.

**Spec:** `docs/requirements/git-conflicts.md` (GC-4, GC-14's backend half,
GC-15, GC-16, GC-19, GC-27, AC-GIT-003.14); D-6.2.

## Global Constraints

- The shared constraints of [the step 4 index](2026-11-08-00-roadmap-step-4.md)
  apply.
- `resolution` by kind; anything else is `409 resolution-not-allowed`:

  | Resolution      | Allowed for                        | Does                                                               |
  | --------------- | ---------------------------------- | ------------------------------------------------------------------ |
  | `mark-resolved` | `editable` files                   | `git add` as saved                                                 |
  | `ours`          | `both-changed`, `both-added`       | `git checkout --ours`, then `git add`                              |
  | `theirs`        | `both-changed`, `both-added`       | `git checkout --theirs`, then `git add`                            |
  | `keep`          | `deleted-by-us`, `deleted-by-them` | `git checkout` of the side that exists, then `git add`             |
  | `delete`        | `deleted-by-us`, `deleted-by-them` | deletes the file if it is there, `git update-index --force-remove` |

- Every git command gets the path literally: `--literal-pathspecs`, or for
  `update-index`, `-z --stdin`.
- Reading a file for its markers and deleting one both go through
  `resolveInWorkingCopy`, also though the path is in the merge's list, and a
  path it refuses is answered as `toFilesError` does.
- A line that looks like a marker (GC-14): it starts with `<<<<<<< ` or
  `>>>>>>> `, or is exactly `=======`; a `\r` at its end does not count.
- `mark-resolved` without `force` on such a file is `409 conflict-markers-left`,
  and nothing changes.
- A file already resolved, or not in the merge, is `409 not-conflicting`.
- It publishes `files.changed`, naming the path's folder, and `git.changed`.

## Review Focus

- **`=======` inside a code block or a table, or `<<<<<<<` without its space,**
  are told apart by exactly GC-14's rule, no more → Task 1 test `recognises only
  GC-14's lines`.
- **A symbolic link or a binary file as a whole version** comes back as it was,
  byte for byte → Task 2 test `resolves a binary file and a symbolic link with a
  whole version`.
- **A name git could read as a pathspec,** such as `:(top)x.md`, is one file →
  Task 2 test `resolves a file with a name like a pathspec`.
- **A file reached through a linked folder** is neither read nor deleted outside
  the working copy (A-7.6) → Task 2 test `refuses a path through a symbolic
  link`.
- **Deleting the last file of a folder** leaves an empty folder that git does
  not track: harmless, and it stays out of the commit → Task 2 test `deletes the
  last file of a folder`.
- **A resolved file stays listed as resolved,** as the rest of the merge needs
  (GC-7), including after `delete` → Task 2 test `still lists a deleted file as
  resolved`.
