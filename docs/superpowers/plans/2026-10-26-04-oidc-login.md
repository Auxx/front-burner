# OIDC Login Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Plan 4 of [the index](2026-10-26-00-roadmap.md): an operator who sets
the OIDC environment variables never sees the onboarding page; the first OIDC
login with `FRONT_BURNER_ADMIN_EMAIL` creates the administrator and logs them
in, and from then on **Log in with OIDC** works like a password login.

**Architecture:** `server/feature/auth` gets an `oidc/` folder. OIDC settings
come from the environment or, for plan 5, from `system_settings` (encrypted
client secret); environment wins (AO-35). `openid-client` does discovery, PKCE,
`state`, `nonce` and ID token validation, with every request going through plan
3's `EgressHttpClient` (A-7.8). The pending `state`, PKCE verifier and `nonce`
live in memory for 10 minutes, bound to the browser by a short-lived cookie; the
callback hands the web client a 60-second one-time code, which the web client
exchanges for the usual session tokens (LG-22). Failures redirect with a reason
code that the web client shows generically, or in full while onboarding is
pending (LG-21, AO-26, AO-34).

**Tech Stack:** as before, plus `openid-client` 6.8.8; dev dependency
`oauth2-mock-server` 9.3.0 for tests.

**Spec:** `docs/requirements/auth-onboarding.md` (AO-1, AO-2, AO-5, AO-12, AO-27
to AO-36, AO-38, AO-39; criteria 8, 9, 11, 12);
`docs/requirements/auth-login.md` (LG-2, LG-7, LG-8, LG-17 to LG-23, LG-24 for
OIDC, LG-41 to LG-43 for OIDC, LG-65; criteria 2, 7, 8, 9). Architecture:
`security.md` A-7.8; `overview.md` A-1.10; `data.md` A-4.4, A-4.8.

## Global Constraints

- The shared constraints of [the index](2026-10-26-00-roadmap.md) apply.
- Plan 1's `SessionService.start`, `LoginAuditService.record`,
  `AuthController.methods()`, `ApiErrorException` and the `login` rate-limit
  group are reused; plan 3's `SecretBox`, `ENCRYPTED_COLUMNS` and
  `EgressHttpClient` likewise. Nothing in this plan calls `fetch` directly.
- No token, code or client secret in a URL the browser sees, except the one-time
  code of LG-22 and the provider's own authorization `code` and `state` on the
  callback.
- The redirect URI is
  `` `${req.protocol}://${req.get('host')}/api/v1/auth/oidc/callback` ``, with
  Express's `trust proxy` (A-1.15) _(plan's call: no public URL variable)_. The
  web client shows the same value in plan 5.
- Fixed texts: "OIDC login failed" (LG-21); "OIDC login is not available right
  now." (LG-7); the env-pending and page-pending reason texts are listed in
  Task 8.
- Tests run the mock provider over HTTPS with plan 3's test certificate; the
  server process gets `NODE_EXTRA_CA_CERTS` pointing at it. Loopback is allowed
  by default (AR-57), so the provider on `localhost` is reachable.

## Review Focus

- **A callback whose `state` cookie is missing** (the user started on another
  device, or the cookie expired) must fail with `state-mismatch`, not log anyone
  in → Task 6 test `refuses a callback without the state cookie`.
- **The same callback URL loaded twice** (reload, back button) must not start a
  second session; the pending login is used once → Task 6 test `uses a pending
  login once`.
- **An ID token whose email differs only in case from the pending administrator
  email** must be accepted (AO-27 is case-insensitive) and the user stored with
  the provider's spelling → Task 5 test `accepts the pending administrator in
  another case`.
- **The provider down at startup** (AO-32) must not stop the backend; the login
  page says OIDC is unavailable, and it becomes available without a restart once
  the provider answers → Task 4 test `retries discovery after a minute`.
- **An OIDC login racing a password login on onboarding** (plan 5 makes both
  possible while pending): the pending administrator must be created at most
  once, and only while the state is still `oidc-pending` → Task 5 test
  `completes onboarding only while it is pending`.

### Task 6: The OIDC login flow

**Files:**

- Create: `libs/server/feature/auth/src/oidc/oidc-login.service.ts` (+

**Interfaces:**

- Consumes: Tasks 4 and 5, `SessionService.start`, `LoginAuditService`.
- Produces:
  - `PendingLogins` (in memory): `add(state, { codeVerifier, nonce, redirectUri
    })`, `take(state)` (returns and deletes; entries older than 10 minutes are
    gone; at most 1 000 entries, oldest dropped first).
  - `OneTimeCodes` (in memory): `issue(userId: number): string` (32 random
    bytes, base64url), `take(code): number | undefined` — valid 60 seconds, once
    (LG-22).
  - `OidcLoginService`:
    - `start(redirectUri: string): Promise<{ authorizationUrl: URL; state:
      string }>` — `randomPKCECodeVerifier`, `calculatePKCECodeChallenge`,
      `randomState`, `randomNonce`, `buildAuthorizationUrl` with `scope`,
      `redirect_uri`, `code_challenge_method: 'S256'` (LG-17);
    - `complete(callbackUrl: URL, cookieState: string | undefined, info:
      RequestInfo): Promise<OidcOutcome>` where `OidcOutcome = { ok: true; code:
      string } | { ok: false; reason: LoginAuditReason }`. It checks that the
      URL's `state` equals `cookieState` and takes the pending login
      (`state-mismatch` otherwise), then `authorizationCodeGrant(config,
      callbackUrl, { pkceCodeVerifier, expectedState, expectedNonce })`. Error
      mapping: `AuthorizationResponseError` → `provider-error` (keep `error` and
      `error_description` for the audit); a network error or timeout →
      `provider-unreachable`; `ResponseBodyError` from the token endpoint →
      `code-exchange-failed`; any ID token check → `invalid-id-token`. Then
      `OidcUserService.resolve`. Every outcome is audited with method `oidc`,
      issuer, subject and the provider's error fields (LG-41, LG-42); failures
      are logged as in LG-47, and a failure while pending also as "OIDC login
      failed while onboarding is pending" (AO-39).
    - `exchange(code: string, delivery: RefreshTokenDelivery, info):
      Promise<IssuedSession>` — `OneTimeCodes.take`, then `SessionService.start
      (user, 'oidc', delivery)` and a `success` audit with the session ID;
      unknown or used code → `ApiErrorException(401, 'oidc-code-invalid')`.
