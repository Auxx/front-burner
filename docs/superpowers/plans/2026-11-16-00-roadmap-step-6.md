# Release — Plan Index

> Status: **Draft**

Plans 104 to 126 finished MVP step 5: every MVP point is built and every MVP
criterion has a test, except ED-10's limited point. This index splits MVP step 6
(`docs/product/mvp.md`, "Order of work": the deployment guide, the security
review and the release checks) into small plans, numbered on from 127. Each plan
is one branch and one pull request, leaves CI green, and can be shown to someone
when it is merged. At the end of step 6 an operator can follow the deployment
guide to a signed, scanned image, every non-functional requirement in the MVP
(section 11 of "In scope") is built and checked, and all twelve exit criteria
hold on a fresh instance, in a desktop browser and on real phones.

## Shared constraints

The shared constraints of the earlier indexes
([step 1](2026-10-26-00-roadmap.md), [step 2](2026-10-28-00-roadmap-step-2.md),
[step 3](2026-11-02-00-roadmap-step-3.md),
[step 4](2026-11-08-00-roadmap-step-4.md),
[step 5](2026-11-14-00-roadmap-step-5.md)) apply to every task of every plan
here, with these additions.

- **Variable names and defaults are A-1.15's.** New variables are parsed by the
  one Zod schema in `server/core/config`, sizes as a number and `KB`, `MB` or
  `GB`, durations in LG-62's format. A secret variable has a `…_FILE` variant
  (NF-8.2).
- **Startup order is A-1.11's and NF's "Startup sequence":** configuration →
  data directory → pre-upgrade snapshot and migrations → encryption key → git →
  recovery (orphans, working copies, jobs) → listening, which is when the
  instance can report ready (NF-9.3).
- **Never delete what may hold unpushed work.** A working copy is moved, never
  removed, by anything this step adds (NF-6.4).
- **Repeating work is a housekeeping job** of the job runner (A-6, `pool:
  'housekeeping'`), like `FinishedJobsCleanup`, not a timer of its own.
- **Logs follow NF-10.4 and NF-10.5:** IDs, never names or paths, at `info`;
  paths only at `debug`.
- **The guide describes the MVP.** Features outside the MVP (SMTP, invitations,
  user management, uploads, key rotation) are not described as if they existed.
  Text that the next release will need again goes into `docs/wiki/todo.md`.
- **The checklist is the record.** Every check of Part E writes its result
  (pass, fail with a link to the fix, or not applicable with the reason) into
  `docs/wiki/release-checks.md`, with the date, the commit and, for hand checks,
  the device and browser versions.
- **No action that needs a secret runs on pull requests from forks.** Release
  jobs run on tags only; actions are pinned to commit SHAs, as now.
- **Verifying a plan's last task:** `npm run format`; `node
  tools/ai-tools/src/bin/doc-ids.mjs check`; `npx nx affected -t
  typecheck,lint,test,build,size-check`; and, when the API changed, `npx nx run
  web-api-client:generate`. CI runs the end-to-end suites too; a plan's steps
  name the ones that prove it.
- **`mvp.md`:** the **Deployment guide** row's **Built in** lists every Part C
  pull request; non-functional requirements are tracked in the checklist, not in
  the "Implementation status" table.

## Left out of these plans

- **Encryption key rotation** (NF-8.4) and **uploads** (NF-1.6, NF-9.7's second
  half): not in the MVP.
- **Remembering the Wrap choice** (ED-10): still limited in the MVP; it waits
  for a decision.
- **The nightly schedule** stays commented out in `nightly.yml`, as it was
  turned off on purpose; plan 154 runs it by hand before the release. Turning it
  back on is the operator's call.
- **An `arm64` image**: the first release is `linux/amd64` only. Plan 139
  records the rest in `docs/wiki/todo.md`.
- **Choosing the version number and pushing the tag** of the first release are
  the operator's: plan 139 builds what a tag starts, and plan 157 says when the
  release is ready.
