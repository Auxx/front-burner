# Repository Management — Plan Index

> Status: **Accepted**

Plans 68 to 103 finished MVP step 4, except the leftovers named in
[its index](2026-11-08-00-roadmap-step-4.md). This index splits MVP step 5
(`docs/product/mvp.md`, "Order of work": the repository management page) into
small plans, numbered on from 104. Each plan is one branch and one pull request,
leaves CI green, and can be shown to someone when it is merged. At the end of
step 5 the operator sees every repository, follows and retries a clone, sees and
fixes repository warnings, changes a repository's credentials and commit author,
clones a damaged working copy again and removes a repository. This is exit
criterion 11 of the MVP.

Step 5 is the last step that builds features: step 6 is the deployment guide and
the release checks. So this index also takes the leftovers of steps 1 to 4 that
are in the MVP and still not built (Part D), so that every MVP point is built
when step 6 starts.

There is no separate design spec: the requirements and the architecture
documents are the spec. Each plan names the requirement IDs it implements and
records its own decisions as _(plan's call)_; a decision that changes or adds to
an architecture document updates that document in the same pull request.

why a clone failed. No plan may offer an action that the backend can't do yet:

## Shared constraints

The shared constraints of [the step 1 index](2026-10-26-00-roadmap.md),
[the step 2 index](2026-10-28-00-roadmap-step-2.md),
[the step 3 index](2026-11-02-00-roadmap-step-3.md) and
[the step 4 index](2026-11-08-00-roadmap-step-4.md) apply to every task of every
plan here, with these additions.

- **Library homes.** Endpoints about the repository itself (list, details,
  removal, cloning again) go into `server/feature/repositories`; the remote
  problems of `sync_state` stay in `server/feature/sync`, which the warnings
  read through `SyncStateStore`. Both pages go into `web/feature-repositories`
  (A-2.2a: "add-repository flow, repository management"). What the dashboard and
  the management page share goes into `web/shell`, next to
  `shell-repository-status`; a feature library never imports another.
- **Another user's repository is a missing one** (RM-1, AC-REPO-003.14): every
  new endpoint finds the row with `RepositoryQueries.find(userId, id)` and
  answers `404 not-found` without it, and every plan has a test that says so.
- **The backend decides what is allowed in which status** (RM-2): retrying a
  clone only in `error`, and removing in every status. The web client only hides
  what the backend would refuse.
- **Secrets never leave the backend** (A-3.5, RM-14): no response carries a
  password, token, private key or a remote URL with credentials; git's error
  text is stored only after the engine has removed credentials (AR-53, NF-10.5).
- **Removing is final.** Nothing of a removed repository is left: rows, jobs,
  working copy, trashed folders, browser drafts on the device that removed it.
  Saved credentials, keys and known hosts stay (RC-10).
- **Events.** `repository.status` when a status changes (as now),
  `repository.warning` (repository ID) when a stored remote problem changes, and
  `repository.removed` (repository ID) when a repository is removed (A-3.11). A
  key's lock already has `key.locked` and `key.unlocked`. Clients read the new
  state over REST, also after a reconnect.
- **Labels are the requirement's.** Statuses, errors and warnings use the exact
  text of RM-6 and RM-8, through the existing `shell-repository-status`.
- **New Angular artefacts come from `toolkit-nx`,** templates follow
  `angular-templates`, and read-only details use the key-value list (A-10.50).
- **Verifying a plan's last task:** `npm run format`; `node
  tools/ai-tools/src/bin/doc-ids.mjs check`; `npx nx affected -t
  typecheck,lint,test,build,size-check`; and, when the API changed, `npx nx run
  web-api-client:generate`. CI runs the end-to-end suites too; a plan's steps
  name the ones that prove it.
- A test that covers only part of a criterion does not start with its ID (the
  step 3 index explains why). Each criterion is named by one plan, as its steps
  say.

## Left out of these plans

Each is deferred to the step that builds it, not dropped:

- **Step 6:** the deployment guide and the release checks, including the hand
  checks on real phones, which now include both new pages.
- **Still limited in the MVP:** remembering the **Wrap** choice (ED-10), which
  `mvp.md` keeps limited although the Preferences page now exists. Building it
  would change the MVP's scope, so it waits for a decision.
- **Not in the MVP:** renaming a repository, changing its remote, clone mode or
  level, managing saved credentials and known hosts as lists, disk usage, and
  removing several repositories at once (REQ-REPO-003, "Out of scope").
