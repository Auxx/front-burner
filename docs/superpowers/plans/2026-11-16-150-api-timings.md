# API Timings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Plan 150 of [the step 6 index](2026-11-16-00-roadmap-step-6.md): a
tool that measures the API targets of NF-2 against a running instance and prints
p95 next to each target, so that plan 152 can run it on the reference host:
opening a folder of 1,000 entries (300 ms), opening a 100 KB Markdown file (200
ms), a save (200 ms), a cold and a warm status and commit in a 100,000-file
repository (NF-2.8's "about 2 seconds"; spike 4's numbers).

**Architecture:** `tools/ai-tools/src/bin/perf-api.mjs` _(the `ai-tools` skill:
tools go there, with a `--help` and an entry in the skill)_. It takes the
instance URL, a login and a repository name, and prepares its own fixtures
through the API and git: a folder of 1,000 files, a 100 KB Markdown file, and,
with `--large`, a generated 100,000-file repository pushed to a local remote and
added (spike 4's generator, `docs/architecture/spikes.md`). It runs each
operation N times (default 50) after 5 warm-up runs, reads the server's own
duration from the `Server-Timing` header _(plan's call: added by this plan to
the request logger's middleware, as `app;dur=<ms>`, so that "API" means "on the
server", as NF-2 says)_, and prints a table: operation, p50, p95, max, target,
pass. A cold run drops the page cache only when run as root on the host
(`--cold`, documented as optional).

**Tech Stack:** Node.js, `fetch`. No new packages.

**Spec:** `docs/architecture/non-functional.md` NF-2.1 to NF-2.3, NF-2.8,
NF-1.4, "Reference host"; `docs/architecture/spikes.md` (spike 4, A-5.14).

## Global Constraints

- The shared constraints of [the step 6 index](2026-11-16-00-roadmap-step-6.md)
  apply.
- The tool only reads and writes in the repository it is given, which it
  creates; it refuses an existing repository with that name.
- `Server-Timing` holds only a duration, never a route or ID, and is sent on
  every API response _(plan's call: it reveals nothing that the response time
  does not)_.
- A local run, on a developer machine, fills the checklist's rows as
  "indicative"; only plan 152's run on the reference host counts.

## Review Focus

- **The client's own network time** in the numbers → the tool uses
  `Server-Timing`, and says so in its output.
- **A run on a machine much faster than the reference host** → the output prints
  the host's CPU count and memory, so a result is never quoted without them.
