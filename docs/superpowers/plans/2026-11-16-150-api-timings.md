# API Timings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Plan 150 of [the step 6 index](2026-11-16-00-roadmap-step-6.md): a
tool that measures the API targets of NF-2 against a running instance and prints
p95 next to each target, so that plan 152 can run it on the reference host:

- opening a folder of 1,000 entries (NF-2.1, 300 ms);
- opening a 100 KB Markdown file (NF-2.2, 200 ms);
- a save (NF-2.3, 200 ms);
- a pull and a push started by the user, against the same operation with plain
  `git` from the host (NF-2.6, at most 1 s added on top of git's network time);
- a cold and a warm status and commit in a 100,000-file repository (NF-2.8's
  "about 2 seconds"; spike 4's numbers).

**Architecture:** Two tools in `tools/ai-tools/src/bin/` _(the `ai-tools` skill:
tools go there, with a `--help` and an entry in the skill)_.

- **`gen-large-repo.mjs`** writes a git repository of 100,000 files, since spike
  4's harness was not kept (`spikes.md`: "a throwaway harness … not kept"). Its
  shape stands in for spike 4's shallow Linux clone _(plan's call)_: a tree
  about 5 levels deep of about 4,500 folders; file sizes drawn from a seeded
  log-normal distribution with a median of 4 KB and a mean of about 12 KB, for
  about 1.2 GB of files; one commit, as spike 4 had; mostly `.c`, `.h` and `.md`
  text with a few binary files. A `--seed` makes runs repeatable, and `--files`
  and `--size` change the count and total. It prints the counts and sizes it
  made, and a `--from <path>` option skips generation and uses an existing clone
  instead (for example Linux, to compare with spike 4).
- **`perf-api.mjs`** takes the instance URL, a login and a repository name, and
  prepares its fixtures through the API and git: a folder of 1,000 files, a 100
  KB Markdown file, a commit to pull, and, with `--large`, the generated
  repository pushed to a local remote and added. It runs each operation N times
  (default 50) after 5 warm-up runs and reads the server's own duration from the
  `Server-Timing` header, so that "API" means "on the server", as NF-2 says. It
  prints a table: operation, p50, p95, max, target, pass. A cold run drops the
  page cache only when run as root on the host (`--cold`, documented as
  optional). NF-2.6's row times the job from request to its `job.finished` event
  and subtracts the median of the same `git pull` or `git push` run by hand
  against the same remote.

`Server-Timing` is off by default. `FRONT_BURNER_SERVER_TIMING=true` turns it
on: `app;dur=<ms>` on every API response.

Two options for the scale of NF-1, which the release checklist (plan 148) found
no check for _(plan 148's finding; how they seed and measure is this plan's
call)_:

- **`--users 10`** runs the measures from 10 sessions at once, each on a
  repository of its own, so that the numbers are those of NF-1.2's 10 active
  users;
- **`--scale`** first fills a stopped instance's data directory with 50 users
  and 50 small repositories each (NF-1.1, NF-1.3: 2,500 working copies), as the
  end-to-end suites' seed does, since the MVP has no API that creates users. It
  then times the start until ready, which recovery stretches by visiting every
  working copy (NF-9.4), and runs the measures among them.

**Tech Stack:** Node.js, `fetch`, `git`. No new packages.

**Spec:** `docs/architecture/non-functional.md` NF-2.1 to NF-2.3, NF-2.6,
NF-2.8, NF-1.1 to NF-1.4, "Reference host"; `docs/architecture/spikes.md` (spike
4, A-5.14); `docs/architecture/overview.md` A-1.15.

## Global Constraints

- The shared constraints of [the step 6 index](2026-11-16-00-roadmap-step-6.md)
  apply.
- The tool only reads and writes in the repository it is given, which it
  creates; it refuses an existing repository with that name. `--scale` is the
  one exception: it writes into the data directory it is given, only while the
  instance is stopped, and refuses one that already holds users other than the
  first administrator.
- `Server-Timing` holds only a duration, never a route or ID. It is sent only
  while `FRONT_BURNER_SERVER_TIMING` is `true` (default `false`); the guide's
  "Logging" table lists it, and `security.md`'s header list says it is off
  unless set. Plan 141 ran before this plan, so the guide does not list it yet:
  plan 141's `deployment-guide.spec.ts` (`npm run check:guide`) fails until it
  does.
- `perf-api.mjs` stops with a message naming the variable when the instance
  sends no `Server-Timing` header.
- A local run, on a developer machine, fills the checklist's rows as
  "indicative"; only plan 152's run on the reference host counts.

## Review Focus

- **The client's own network time** in the numbers → the tool uses
  `Server-Timing`, and says so in its output.
- **A run on a machine much faster than the reference host** → the output prints
  the host's CPU count and memory, so a result is never quoted without them.
- **The header leaking in production** → test `no Server-Timing by default`.
- **A generated repository that is not like a real one** (all files the same
  size, one flat folder) → the generator prints its shape, and the checklist
  quotes it next to the numbers.
