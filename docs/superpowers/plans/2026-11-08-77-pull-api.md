# Pull API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Plan 77 of [the step 4 index](2026-11-08-00-roadmap-step-4.md): `POST
…/git/pull` starts a job that fetches and then merges, and either ends with a
count or leaves a merge in progress.

**Architecture:** The job runs `FetchStep` under the network lock, then the
merge inside `WorkingTreeGuard.change`, with the checks made again there, since
a save can arrive during the fetch (A-5.3). The question of CA-14 can be
answered only after the fetch, so it is an outcome:
`commit-author-not-confirmed` before anything is merged. The client asks and
pulls again _(plan's call: one path, instead of a guess at the request from
counts that may be old)_. The record is written to `sync_state` just before a
merge that will change something, with `merge_applying` set while git runs,
which tells recovery (plan 78) a merge cut short from one waiting for the user.
It keeps the record it replaces, so that a pull that fails or is aborted does
not take **Undo merge** away from an earlier merge (GC-25) _(plan's call)_.

A branch with no upstream can have a remote branch of its name: a push is then
rejected, and "Pull first" must lead somewhere (GA-30). So **Pull** also works
for an unpublished branch when `origin/<branch>` exists, and makes it the
upstream. A push rejected as non-fast-forward fetches afterwards, so that the
ref exists and the counts are right _(plan's call; it updates GA-8)_.

**Tech Stack:** as before. No new packages.

**Spec:** `docs/requirements/git-advanced.md` (GA-3, GA-4, GA-8's backend half,
GA-25 to GA-28, GA-43); `docs/requirements/commit-author.md` (CA-1, CA-14);
`docs/requirements/repo-credentials.md` (RC-3, RC-4, RC-19, the API for
AC-REPO-002.2); `docs/architecture/data.md` A-4.5a; D-4.3, D-4.6.

## Global Constraints

- The shared constraints of [the step 4 index](2026-11-08-00-roadmap-step-4.md)
  apply.
- The job type is `sync.pull`, dedupe key `pull:<repositoryId>:<branch>`,
  `onInterrupted: 'fail'`, `maxAttempts: 1`. Its payload is `{ branch }`.
- The request refuses, in this order, with `409`: `merge-in-progress`,
  `no-branch`, `no-upstream` (no commits, `upstreamGone`, or unpublished without
  `sameNameRemote`), `uncommitted-changes`, then `key-locked` or
  `credentials-missing`.
- Inside the lock, each of these ends as a `failed` outcome, with nothing
  merged: `merge-in-progress`, `branch-changed`, `no-upstream` (the fetch
  removed it), `uncommitted-changes`, `commit-author-not-confirmed`,
  `merge-blocked`, whose `paths` param lists the ignored files.
- The record, in order, inside the lock:
  - `GitMerge.isUpToDate`: the result is `up-to-date`, and no record is touched,
    so that **Undo merge** of an earlier merge stays.
  - Otherwise `startMerge`, then the merge.
  - `fast-forward`: `forgetRecord`, as the branch has moved past any earlier
    merge.
  - `merged`: `mergeCommitted`.
  - `conflicted`: `mergeStopped`, and the record stays until the merge ends
    (A-4.5a).
  - `merge-blocked`: `restoreEarlier`, as nothing changed.
  - Any other failure: `GitMerge.undoCutShort`, then `restoreEarlier`.
- An unpublished branch with `origin/<branch>` gets `GitMerge.adoptUpstream`
  inside the lock, once the checks have passed. It stays after an abort: the
  branch and the files are as they were, and the upstream is the one the user
  asked to pull from.
- `PushJob`, inside the network lock, ends with a `failed` outcome of
  `merge-in-progress` when a merge started after it was queued (GC-3). When the
  remote rejects it as `push-non-fast-forward`, then, once the network lock is
  released, as `FetchStep` takes it, it runs `FetchStep`, whose failure changes
  nothing about the outcome. For that rejection, `GitEngine.push` keeps the
  refspec it added in a single-branch clone, as the remote branch exists
  (GA-41).
- It publishes `git.changed`, and `files.changed` with `folders: 'all'` when the
  merge changed files (FB-41).

## Review Focus

- **A save that arrives while the pull fetches** must stop it before the merge,
  or git refuses or, worse, merges under the user's text → Task 2 test `refuses
  a save made during the fetch`.
- **A merge that times out or crashes partway** leaves the working copy as it
  was (GA-43) → Task 2 test `a merge that fails is undone`.
- **The user switching branch between queueing and running** must not merge
  another branch's upstream → Task 2 test `refuses when the branch changed`.
- **Ignored files** do not count as uncommitted changes, so that a repository
  with `.gitignore`d output can pull → Task 2 test `pulls with only ignored
  files around`.
- **A commit-author question after the fetch:** the fetched commits stay,
  nothing is merged, and the second pull goes on → Task 2 test `asks for the
  author only when a merge commit is needed`.
- **A branch named like a remote branch,** in a full clone and a single-branch
  one, with the remote branch newer than the last fetch: push, "Pull first",
  pull, push must work → Task 2 test (end to end) `a rejected branch can pull
  and push`.
- **A pull that changes nothing, or fails, after an unpushed merge** must keep
  what the earlier merge can undo → Task 1 test `gives the earlier record back`,
  and Task 2 test `leaves the record alone when nothing is to merge`.
- **A merge killed at its timeout** leaves `index.lock`, and the undo must still
  work → Task 2 test `a merge that fails is undone`, with the lock left behind.

### Task 1: The record in sync_state

**Files:**

- Modify: `libs/server/core/database/src/schema/sync-state.ts`, the migration
  from `npx nx run server-core-database:db-generate`,
  `libs/server/feature/sync/src/state/sync-state.store.ts` (+ spec),
  `docs/architecture/data.md`

**Interfaces:**

- Produces: columns `recorded_commit`, `merge_commit`, `earlier_recorded_commit`
  and `earlier_merge_commit` (text, nullable) and `merge_applying` (boolean,
  default false), and on `SyncStateStore`:
  - `startMerge(repositoryId: number, recordedCommit: string): void`, which
    moves the record to the `earlier_` columns, and sets `merge_applying`;
  - `mergeStopped(repositoryId: number): void`, which clears `merge_applying`,
    for a merge that waits for the user;
  - `mergeCommitted(repositoryId: number, mergeCommit: string): void`, which
    also clears the `earlier_` columns;
  - `restoreEarlier(repositoryId: number): string | null`, which puts the
    `earlier_` columns back, clears `merge_applying`, and returns the recorded
    commit, for `GitMerge.keepRecord` or, when `null`, `GitMerge.forgetRecord`;
  - `record(repositoryId: number): { recordedCommit: string | null; mergeCommit:
    string | null; applying: boolean }`;
  - `forgetRecord(repositoryId: number): void`.
