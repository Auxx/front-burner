**Goal:** Plan 111 of [the step 5 index](2026-11-14-00-roadmap-step-5.md):
`DELETE /repositories/:id` removes a repository in any status: it cancels its
jobs, deletes its rows at once, and deletes its working copy in a job, as
`docs/architecture/jobs.md` describes for **Remove repository**.

**Architecture:** The request does what must be immediate, inside the
working-tree lock: it checks again what would be lost (plan 110), cancels the
repository's jobs and waits for a running clone to settle, deletes the row (its
`sync_state` and `jobs` go by cascade, A-4.5b), moves the working copy into
`tmp/` under a trash name, and queues `repositories.delete-working-copy`. The
job deletes the folder and the repository's trashed folders (`emptyTrashOf`).
The name is free at once, as the row is gone (RM-20).

**Tech Stack:** as before. No new packages.

**Spec:** `docs/requirements/repo-manage.md` (RM-1, RM-2, RM-17 to RM-21,
AC-REPO-003.12, AC-REPO-003.13); `docs/architecture/jobs.md` (**Remove
repository**); A-4.5b; NF-2.8.

## Global Constraints

- The shared constraints of [the step 5 index](2026-11-14-00-roadmap-step-5.md)
  apply.
- The confirmation: query `confirmName`. When the check of plan 110 says work
  would be lost and `confirmName` is not the repository's name exactly (after
  trimming spaces), the answer is `409 removal-needs-confirmation` with the
  check's counts as params, and nothing changes. When nothing would be lost, no
  name is needed _(plan's call: a query, as a `DELETE` body is not portable)_.
- `JobRunner.cancel` gains a `repositoryId` filter. Every job of the repository
  is cancelled: the clone, fetches, a push or pull that waits. A cancelled
  running clone is awaited (bounded by A-1.14's grace) before the folder moves,
  so that it cannot rename a finished clone into place afterwards (review's
  focus). After review: no job passed its signal to git, so cancelling stopped
  nothing; `GitRunner` now kills git when a run's signal fires, and the clone,
  fetch, push and pull jobs pass theirs. Only the clone is awaited, inside the
  working-tree lock: a pull or a push waits for that lock, so waiting for them
  would hold the request for the whole grace. The move and the row's deletion
  run inside the network lock too, which a fetch or a push holds until its git
  has ended; the working copy moves first, so that a failed move deletes
  nothing; and the lock marks the repository removed, so that what waited for it
  answers `404`.
- The trash name is `remove-<repositoryId>-<uuid>`, made like `newTrashName` in
  `trash.ts`, never from the user (A-6.3). `tmp/` is emptied on start (NF-5.1),
  so a restart before the job ran leaves nothing behind.
- The delete job is in the `housekeeping` pool and is not tied to the repository
  row, which no longer exists: its `repositoryId` is `null`, and the ID and
  trash name are in its payload.
- Key unlocks, saved credentials and known hosts are untouched (RC-10).
- Publishes `repository.removed` (repository ID) to the owner. The response is
  `204`.

## Review Focus

- **Work that would be lost, without the name:** nothing changes → test `refuses
  without the name when work would be lost`.
- **A file saved between the dialog and the confirmation** is caught by the
  second check → test `checks again inside the lock`.
- **A clone in progress** is cancelled, and no folder appears afterwards → test
  `AC-REPO-003.13: removing a repository that is cloning cancels the clone`.
- **A background fetch** queued or running is cancelled → test `cancels its
  fetch jobs`.
- **A restart between the move and the delete** leaves nothing, as `tmp/` is
  emptied on start → test `a leftover removed working copy is deleted on start`.
- **The name** can be used for a new repository at once → test `the name is free
  at once`.
- **Saved credentials** remain → test `keeps the saved credentials`.
