# Unlock Dialog and Banner Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Plan 60 of [the step 3 index](2026-11-02-00-roadmap-step-3.md):
opening a repository whose key is locked shows a banner with **Unlock**, and
pressing **Push** with a locked key asks for the passphrase and then carries on
by itself.

**Architecture:** `UnlockKeyDialog` goes in `web/repository-dialogs`, since the
management page uses it in step 5. A page-provided `LockedKeyService` reads plan
59's endpoint for the banner, and hides it on `key.unlocked`.
`PushService.start` opens the dialog on `409 key-locked`, and retries when it
closes with success, so that the user never presses **Push** again (RC-17).

**Tech Stack:** as before. No new packages.

**Spec:** `docs/requirements/repo-credentials.md` (RC-4's **Unlock**, RC-15
except its fetch clause, RC-16, RC-17, RC-18's texts, RC-20, RC-25; criteria 9,
10, 15, the banner half of 8); `docs/requirements/navigation.md` NV-16.

## Global Constraints

- The shared constraints of [the step 3 index](2026-11-02-00-roadmap-step-3.md)
  apply.
- The banner says "_&lt;key name&gt;_ is locked. Unlock it to fetch, pull and
  push." with **Unlock**. It blocks nothing else, and it can be dismissed for
  the rest of the visit (RC-15). It is shown below the bar (NV-16), and
  announced once (RC-25).
- The dialog shows the key's name, type and fingerprint and a masked, required
  **Passphrase** field (RC-16). Its field has `autocomplete="off"`. A passphrase
  is never put in a signal that outlives the dialog, or in browser storage
  (AR-17).
- Errors on the field: "Wrong passphrase", and "Too many attempts. Try again in
  a minute." (RC-18). The backend answers the second with `429
  unlock-too-many-attempts`, which has no `fields` (plan 59), so the client puts
  it on the field itself.
- The **Add repository** form's passphrase for a saved key counts toward the
  same limit (plan 59). Its `failureTexts` shows the 429 above the buttons
  today; this plan moves it onto `credentials.passphrase` too, as RC-18 says.
  _(Found in plan 59's review.)_
- A key whose secret is `missing` (NF-8.6) is not offered **Unlock**: the
  endpoint of plan 59 reports `missing`, and unlocking it can only fail with
  `credentials-missing`.
- Cancelling the dialog from a push cancels the push, with no message (RC-17).

## Review Focus

- **The unlock ending meanwhile** (idle time), with the banner already gone →
  the push still gets `key-locked` and asks → Task 2 test `asks when the key
  locked itself after the banner went away`.
- **Unlocking in another tab of this session** must remove this tab's banner,
  and close nothing else → Task 2 test `removes the banner on key.unlocked`.
- **Another session's unlock** must leave the banner → end-to-end test
  `AC-REPO-002.15`.
- **A dismissed banner** comes back on the next visit, not while this visit
  lasts, and **Push** still asks → Task 2 test `a dismissed banner stays away
  for the visit`.
- **Enter in the passphrase field, twice,** sends one attempt, because each
  counts toward the limit → Task 1 test `sends one attempt for two quick
  submits`.
